# Mada Mobile — UI/UX Handoff (R04 Instructor)

**الإصدار:** 0.2 — اتجاه جاهز للتنفيذ والمراجعة
**النطاق المفترض:** نسخة الموبايل الأولى للمدرب R04، Android وiOS، عربية افتراضيًا وRTL.
**مصدر الحقيقة:** API الحالي في `backend/MadaAcademy.Api/`، وليس البيانات الظاهرة في الصور التجريبية.
**ملاحظة:** الصور نماذج شكلية وليست تطبيقًا عاملًا؛ الأسماء والمواعيد والأعداد فيها أمثلة فقط. المواصفات والسلوك أدناه هي المرجع عند التنفيذ.
**قواعد التنفيذ الملزمة:** [قواعد تأسيس تطبيق الموبايل](MOBILE_FOUNDATION_RULES_AR.md) — الخطوط، التوكنز، البنية، المصادقة، وصلاحيات الأدوار.
**مصفوفة التنفيذ:** [الشاشات والـAPI والصلاحيات](MOBILE_SCREEN_API_PERMISSION_MATRIX_AR.md) — الـendpoints الفعلية، حماية Backend، وحالة كل شاشة.

## 1. قرار التصميم

التطبيق ليس نسخة مصغّرة من لوحة الإدارة. يبدأ المدرب من **مهمته الأهم الآن**، ثم ينتقل إلى الجدول أو المهام أو الحساب. كل مهمة تفتح وجهتها مباشرة. التنبيهات معلوماتية، أما المهام فتحتاج إجراء؛ لا نكرر الشيء نفسه في أكثر من مكان.

**النسخة الأولى تركّز على:** تسجيل الدخول، أولويات اليوم، الجدول، تفاصيل الجلسة، الحضور، وتقييم المدرب. نضيف أدوار ولي الأمر والطالب والإدارة في مراحل لاحقة فوق نمط التنقل نفسه، لا في النسخة الأولى.

### خارج نطاق النسخة الأولى

- تطبيق ولي الأمر/الطالب كاملًا أو نقل كل مساحات R00–R09 إلى الهاتف.
- WebView للوحة الويب.
- العمل دون اتصال للحضور قبل وجود سياسة مزامنة آمنة وidempotency.
- Push أصلي قبل إضافة تسجيل وإلغاء تسجيل device tokens ومزود الإرسال في الخلفية.
- تغيير قاعدة البيانات أو إنشاء Backend موازٍ.

## 2. خريطة التنقل

| الوجهة        | الغرض                                                    | المدخل الرئيسي                 |
| ------------- | -------------------------------------------------------- | ------------------------------ |
| **الرئيسية**  | أعلى أولوية الآن، ثم المهمة التالية، ثم تحديث واحد مختصر | أول تبويب بعد تسجيل الدخول     |
| **الجدول**    | جلسات اليوم والأيام القادمة بترتيب زمني                  | تبويب الجدول أو رابط من المهمة |
| **المهام**    | إجراءات تنتظر المدرب، مع فصل «مطلوب مني» عن «تمت»        | تبويب المهام أو زر المهمة      |
| **حسابي**     | الملف الشخصي، إعدادات اللغة/المساعدة، تسجيل الخروج       | تبويب الحساب                   |
| **التنبيهات** | تحديثات النظام غير المقروءة؛ كل تنبيه يفتح وجهته         | أيقونة الجرس في رأس الشاشة     |

لا نجعل التنبيهات تبويبًا خامسًا ولا نكرر بطاقة التنبيه نفسها كأنها مهمة. كل الشاشات تستخدم زر رجوع أصليًا داخل التدفقات.

## 3. خريطة الشاشات والسلوك

### 3.1 تسجيل الدخول

- رقم الهاتف وكلمة المرور، مع إظهار/إخفاء كلمة المرور.
- حالات: فارغ، تحقق محلي، إرسال جارٍ، بيانات غير صحيحة، حساب مقفل/محاولات كثيرة، انقطاع شبكة.
- لا نظهر مسار OTP أو «نسيت كلمة المرور» كوظيفة جاهزة: SMS الإنتاجي واستعادة كلمة المرور غير مكتملين حاليًا.
- النسخة الحالية ترسل `accountType: "staff"` داخليًا؛ لا تعرض اختيارًا للدور. هذا نوع دخول وليس role.
- بعد النجاح: `GET /api/v1/me` ثم توجيه المستخدم حسب الدور؛ في هذا الإصدار يجب أن يكون R04.

### 3.2 الرئيسية — الأولويات

ترتيب المحتوى من أعلى لأسفل:

1. رأس صغير: شعار مدى، اسم المدرب، جرس التنبيهات.
2. «مهمتك الآن»: جلسة قريبة أو إجراء مؤكد من الـAPI، مع الوقت والمجموعة وزر واحد واضح.
3. «بعدها»: إجراء تالٍ أقل أولوية، مثل تقييمات مستحقة، دون بطاقة ضخمة ثانية.
4. تحديث معلوماتي واحد/ملخص غير مقروء مع رابط للوجهة.

لا نعرض KPIs ورسومًا أو أعداد طلاب/تقييمات إذا لم تصل من عقد موثوق. إذا لا توجد مهام، نظهر حالة فارغة هادئة وروابط للجدول والمهام. أثناء التحميل تظهر skeleton؛ عند الفشل نظهر رسالة وإعادة المحاولة، ولا نعرض بيانات DEMO بدل LIVE.

**حد API مهم:** `GET /api/v1/sessions?from=...&to=...` و`GET /api/v1/scheduling/notifications?unreadOnly=true` موجودان ويمكنهما تشغيل البداية. قائمة الجلسات لا تعطي وحدها دائمًا ملخص الحضور وعدد تقييمات العمل؛ لا ننفذ N+1 طلبات على كل جلسة لافتعال الأولويات. عندما نحتاج ترتيبًا كاملًا من جهة الخادم، نضيف عقدًا مجمّعًا مثل `GET /api/v1/instructor/home-priorities?date=...`، ويظل هذا **endpoint مقترحًا جديدًا** لا ندّعي وجوده الآن.

### 3.3 الجدول

- اختيار يوم/أسبوع قابل للتمرير أفقيًا، مع تمييز اليوم.
- قائمة زمنية، وقت واضح ثم اسم الدورة والمجموعة وحالة الجلسة.
- إبراز الجلسة التالية فقط، مع انتقال مباشر لتحضير الحضور إذا كانت الجلسة تسمح بذلك.
- الأوقات والتواريخ تظهر حسب المنطقة الزمنية المعتمدة للأكاديمية؛ لا نحولها عشوائيًا حسب إعداد الجهاز.
- حالات: تحميل، يوم بلا جلسات، خطأ قابل لإعادة المحاولة، جلسة ملغاة/مكتملة.

### 3.4 تفاصيل الجلسة والحضور

- ملخص مختصر: الدورة، المجموعة، الوقت، الفرع/القاعـة إذا أعادهما الـAPI.
- قائمة أسماء الطلاب وحالة كل طالب.
- اختيار حاضر/غائب ظاهر ومضغوط لكل صف؛ «تأخر» و«بعذر» يظلان متاحين من اختيار ثانوي واضح، لا ندفنهما ولا نخلطهما باللون وحده.
- الصف غير المحدد يبقى غير محدد محليًا؛ لا نرسل `UNMARKED` إلى API.
- زر حفظ ثابت أسفل الشاشة، مع عدد غير المحدد وسبب تعطيل الزر إن كان ذلك شرطًا لتدفق الإرسال. بعد النجاح نحدّث الحالة ونظهر تأكيدًا؛ عند الفشل نبقي المسودة المحلية ونعرض إعادة المحاولة.
- الحفظ يستخدم `PUT /api/v1/sessions/{sessionId}/attendance` مع `records` وحالات backend المدعومة: `PRESENT`, `LATE`, `ABSENT`, `EXCUSED`.
- لا نعلّم الجلسة مكتملة تلقائيًا عند حفظ الحضور؛ إتمام الجلسة إجراء مستقل ومقيّد بالصلاحية.

### 3.5 التقييم

- قائمة التقييمات المستحقة ← طالب واحد ← نموذج تقييم مختصر.
- **توافق العقد الحالي:** مسار R04 الحي وAPI يحفظان `score` واحدة (0–100) و`notes` بناءة لكل طالب، ثم `DRAFT` أو `SUBMITTED`. شاشة الموبايل الأساسية تستخدم درجة إجمالية واحدة وملاحظة بناءة، وخياري «حفظ كمسودة» و«إرسال للمراجعة».
- التقييم لا يُنشر للأسرة من شاشة المدرب؛ الاعتماد/النشر يتم في تدفق المراجعة المصرح به.
- الصور ذات الثلاثة معايير لا تُعتمد كمواصفة للنسخة الأولى؛ معيار التقييم المتعدد يحتاج قرار منتج وتعديل API/DTO واختبارات قبل تصميمه.
- عند الإرسال، يلزم score وملاحظة بناءة وفق العقد الحالي؛ نعرض تحققًا واضحًا قبل الإرسال.

### 3.6 المهام والتنبيهات

- «مطلوب مني» و«تمت» للتكليفات التي تتطلب إجراءً.
- «تحديثات» منفصلة بصريًا، مثل تغيير موعد جلسة؛ النقر يفتح الجدول أو تفاصيل الجلسة.
- التنبيهات الحية من `GET /api/v1/scheduling/notifications?unreadOnly=true`، وتعليم المقروء عبر `POST /api/v1/scheduling/notifications/{notificationId}/read`.
- إذا لم يوجد endpoint مجمّع للمهام، نعرض فقط ما نستطيع إثباته من الـAPI ولا نختلق قائمة مهام كاملة في العميل.

## 5. خريطة الربط بالـAPI الحالي

| تجربة المستخدم         | الطلب الحالي                                                      |
| ---------------------- | ----------------------------------------------------------------- |
| دخول الموظف            | `POST /api/v1/auth/login` مع `accountType: "staff"`               |
| تجديد الجلسة           | `POST /api/v1/auth/refresh`                                       |
| ملف المستخدم/الدور     | `GET /api/v1/me`                                                  |
| جلسات ضمن مدى زمني     | `GET /api/v1/sessions?from=...&to=...`                            |
| تفاصيل جلسة            | `GET /api/v1/sessions/{sessionId}`                                |
| قراءة الحضور           | `GET /api/v1/sessions/{sessionId}/attendance`                     |
| حفظ الحضور             | `PUT /api/v1/sessions/{sessionId}/attendance`                     |
| قراءة/حفظ التقييم      | `GET/PUT /api/v1/scheduling/sessions/{sessionId}/evaluations`     |
| إرسال التقييم للمراجعة | `POST /api/v1/scheduling/sessions/{sessionId}/evaluations/submit` |
| التنبيهات              | `GET/POST /api/v1/scheduling/notifications...`                    |

عميل Mobile موحد يضيف `Authorization: Bearer`, يفك غلاف الاستجابة `data`, يوحّد أخطاء `401/403/409/422/5xx`، ويجرب refresh مرة واحدة مع single-flight عند الطلبات المتزامنة. Access token في الذاكرة قدر الإمكان؛ refresh token في `expo-secure-store`. لا نخزن كلمات مرور أو tokens في logs أو `AsyncStorage` غير المشفر. الـAPI يشتق tenant/branch/permissions من الهوية ولا نرسلها كسلطة من العميل.

## 6. بنية Expo المقترحة

الـworkspace الحالي يحتوي `apps/*` و`packages/*`؛ لذلك `apps/mobile` يدخل تلقائيًا بمجرد وجود `package.json`.

```text
apps/mobile/
├── src/
│   ├── app/                 # Expo Router routes/layouts، رفيعة
│   ├── api/                 # API client typed ومعالجة الأخطاء
│   ├── auth/                # AuthProvider والهوية والتخزين الآمن
│   ├── authorization/       # Role catalog وسياسات route/permission
│   ├── components/          # MadaText وAppUi ومكونات Native مشتركة
│   ├── theme/               # tokens.ts وfonts.ts والطباعة
│   └── features/            # تُضاف وحدات النطاق عند تنفيذها
│       ├── instructor-home/
│       ├── schedule/
│       ├── attendance/
│       ├── evaluations/
│       └── notifications/
├── assets/
├── app.json
├── package.json
└── tsconfig.json
```

هذا هو الهيكل المعتمد الحالي؛ `src/features/` تتوسع مع تنفيذ تدفق حي ولا تُستخدم كملفات شكلية. `client/` يظل واجهة React للويب، و`client-angular/` يظل عميلًا موازيًا، و`backend/` يظل ASP.NET Core. يمكن مشاركة DTOs مستقرة لاحقًا في حزمة typed مشتركة؛ لا نشارك مكونات DOM أو CSS مع React Native.

## 7. خطوات التنفيذ المقترحة

1. إنشاء `apps/mobile` عبر Expo Router + TypeScript، إضافة اسم `@mada/mobile` وسكربتات مستقلة، ثم `pnpm install`.
2. إعداد `EXPO_PUBLIC_API_URL` لكل بيئة؛ عنوان الهاتف الحقيقي لا يستخدم `localhost` الخاص بالحاسوب، والإنتاج/Staging عبر HTTPS.
3. بناء تسجيل الدخول وAuthProvider وتجديد/إنهاء الجلسة باستخدام `expo-secure-store`؛ التحقق من R04 بعد `/me`.
4. بناء API client typed وإضافة TanStack Query أو طبقة server-state مماثلة، ومعالجة الأخطاء والـrefresh المتزامن.
5. تنفيذ Home بحالات loading/error/empty أولًا من `sessions` و`notifications` الحقيقية، دون أرقام غير متاحة.
6. تنفيذ Schedule ثم تفاصيل الجلسة والحضور، واختبار كل حالات الحضور المطلوبة مع الـAPI.
7. تنفيذ قائمة المهام والتقييم بالدرجة الإجمالية والملاحظة المتوافقتين مع العقد الحالي.
8. اختبار Android Emulator وiOS Simulator ثم جهاز فعلي: RTL، لوحة المفاتيح، token refresh، انتهاء الجلسة، شبكة ضعيفة، وإمكانية الرجوع.
9. بعد قبول رحلة R04، إضافة endpoint مجمّع للأولويات إذا أثبت القياس الحاجة، ثم توسيع المنتج لدور آخر بقرار مستقل.

## 8. شروط قبول التصميم قبل إغلاق هذه الشريحة

- المدرب يصل من Home إلى الحضور خلال تفاعل واضح واحد، ويرى سبب أي زر معطّل.
- لا يعرض التطبيق session/notification/score وهمية عند فشل أو فراغ الـAPI.
- لا يستطيع المستخدم قراءة أو تعديل جلسة خارج الصلاحية؛ الاختبار الأساسي على الـbackend وليس اعتمادًا على إخفاء الشاشة.
- الحضور يميّز `UNMARKED` محليًا عن الحالات القابلة للحفظ، ويعالج أخطاء التعارض والتحقق برسالة قابلة للفهم.
- التقييم يستخدم عقد الدرجة الواحدة والملاحظة، ويمر عبر مراجعة رئيس المدربين قبل النشر.
- كل شاشة لها Loading / Empty / Error / Forbidden / Retry حيث ينطبق.
- Arabic RTL واختبارات شاشة صغيرة وVoiceOver/TalkBack وأهداف لمس واضحة.
- Cairo/Inter والأوزان والـRTL متسقة مع الويب على Android وiOS، ولا يظهر fallback مؤقت لخط النظام بعد تحميل التطبيق.
- تحقق `pnpm --filter @mada/mobile typecheck` واختبارات الوحدة؛ واختبارات API/الصلاحيات عبر اختبارات .NET/CI القائمة.
