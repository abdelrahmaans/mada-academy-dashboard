# مصفوفة شاشات Mada Mobile والـAPI والصلاحيات

**آخر تحقق من المصدر:** 2026-10-13 — الفرع `feat/mobile-expo-role-auth`؛ المصفوفة تعكس ربط الشاشات الحية وفحوص RBAC الحالية.
**النطاق:** تطبيق Expo الحالي على Android وiOS. المساحة الوحيدة المفعّلة في v1 هي المدرب `R04_INSTRUCTOR`.

## كيف تقرأ المصفوفة؟

- **صلاحية التطبيق** تعني شرط إظهار route أو الإجراء في `apps/mobile/src/authorization/routeAccess.ts`، وتُحمّل مفاتيحه من `GET /api/v1/me`.
- **حماية Backend** هي ما يفرضه الخادم فعلًا: permission key من كتالوج الدور، ثم الدور والنطاق وإسناد الجلسة أو صلاحية إشراف المجموعة. إخفاء الزر ليس بديلًا عن تحقق الخادم.
- **الحالة** تفرّق بين route موجودة وبين API موجود في الخادم. وجود endpoint لا يعني أن الموبايل يستدعيه بالفعل.
- كل المسارات أدناه نسبية إلى `/api/v1` ما لم يُذكر العكس.

## 3. صلاحيات شاشة مراجعة التقييمات — خارج v1

هذه ليست شاشة المدرب التي تكتب التقييم؛ إنها شاشة اعتماد/إرجاع تقييم، ولا يوجد لها route Mobile حاليًا:

| الإجراء                          | Endpoint                                                      | صلاحية/شرط متوقع                                                                                                  | تحقق Backend الحالي                                                                             |
| -------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| قائمة التقييمات المرسلة للمراجعة | `GET /scheduling/evaluation-reviews` | `R03_HEAD_INSTRUCTORS` + `evaluations.review` + إسناد إشرافي صالح. R04 لا يملك صلاحية المراجعة حتى لو مُنح assignment قراءة/قرار. | يقبل handler R03 فقط مع `evaluations.review`، ثم يحصر النتائج بإسناد المجموعة وصلاحية القراءة/القرار. |
| ملخص حالات المراجعة | `GET /scheduling/evaluation-status-summary` | `evaluations.review` مع دور R03 ونطاق فرع صالح. | permission key مطلوب، ثم يحصر الملخص في المجموعات المسندة. |
| اعتماد/إرجاع للتعديل | `POST /scheduling/evaluation-reviews/{evaluationId}/decision` | `R03` + `evaluations.review` + إسناد يسمح بـ`CanDecideEvaluations`. | يتحقق handler من الـpermission، وقرار `PUBLISH` أو `REQUEST_CHANGES`، والنطاق والإسناد وصلاحية القرار. |

> **تنبيه اتساق:** مسارات تشغيل R03/R04 ومراجعة/كتابة التقييم تستخدم الآن permission keys من `RoleCatalog` إلى جانب تحقق الدور والنطاق والإسناد. assignment إشرافي لا يمنح permission key غير موجود في `/me`. مسارات المراجعة لـR03 منفصلة عن كتابة المدرب لـR04.

## 5. الخلاصة التشغيلية

**الموجود اليوم:** هيكل Expo والتنقل، دخول الموظف واستعادة JWT، `/me` وحراسة fail-closed، وHome/Schedule/Tasks مع جلسات live، وتدفقا الحضور والتقييم Native. فحوص R03/R04 متطابقة مع مفاتيح الصلاحيات في الخادم، وتغطيها اختبارات تكامل.
**المتبقي:** لا يوجد work-queue/summary دقيق للمهام، ولا notification center UI أو Push. لم يُختبر المسار على staging بحسابات حقيقية. ملفات EAS profiles جاهزة محليًا، لكن لا يوجد EAS project ID أو EXPO_PUBLIC_API_URL للبيئات بعد؛ لذلك لم يبدأ build سحابي/موقّع. الأصول الرسمية للهوية لم تُوفر بعد.
**المبدأ:** الواجهة تستخدم permission keys لتوجيه المستخدم، لكن Backend يظل صاحب القرار النهائي على الدور والنطاق والإسناد وكل mutation.

## ملاحظة أمنية ملحقة — صلاحية قراءة الجلسات

**الحالة الحالية:** يشترط `GET /api/v1/sessions` و`GET /api/v1/sessions/{sessionId}` أحد المفتاحين `sessions.read` أو `sessions.assigned.read` من `RoleCatalog` قبل الاستعلام. R03 يقرأ عبر الأول، وR04 عبر الثاني مع فلترة الجلسات المسندة/المشرف عليها؛ الأدوار التي لا تملك أيًا منهما — ومنها R01 وR07 حاليًا — تُرفض بـ403، وتغطي ذلك اختبارات تكامل سلبية.

يُغلق هذا فشل السماح الافتراضي للأدوار الأخرى؛ وتبقى فحوص النطاق والإسناد للمستخدمين المخوّلين شرطًا مستقلًا عن permission key. أي دور جديد يحتاج قراءة الجلسات يجب أن يحصل على مفتاح صريح في `RoleCatalog` واختبار يثبت السماح/المنع؛ إخفاء تبويب الجدول لا يحمي endpoint.
