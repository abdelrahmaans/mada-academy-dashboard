# قواعد تأسيس تطبيق Mada Mobile

**الحالة:** قواعد تنفيذ ملزمة لنسخة الموبايل الأولى، ومكمّلة لـ[UX handoff](UX_HANDOFF_AR.md).
**النطاق الحالي:** Expo + TypeScript، Android وiOS، مساحة المدرب R04 أولًا.

## 1. مصدر الحقيقة للتصميم

- مرجع الألوان والمسافات والزوايا هو `packages/mada-tokens/tokens.css`، وتطبيق الويب يطبّق ثيمه في `client/src/components/MadaTheme.css`.
- نسخة React Native موجودة في `apps/mobile/src/theme/tokens.ts`. هي مرآة للتوكنز وليست نظام ألوان مستقلًا. أي تغيير في اللون أو الزوايا أو الظلال يجب أن يحدّث المرجع والنسخة المحمولة في التغيير نفسه.
- قيم التوكنز الحالية تشمل Teal `#0D9488`، Teal dark `#08776C`، Navy `#14243A`، Amber `#D49A2D`، خلفية `#F4F7FA`، سطح `#FFFFFF`، حدود `#E8EDF2`، ونص ثانوي `#78879A`. الألوان المساندة والخطأ تطابق `MadaTheme.css`.
- الإيقاع للمسافات مبني على 4/8dp؛ نصف قطر العناصر 9–19dp؛ البطاقات هادئة وحدودها خفيفة. لا تُضف ألوانًا أو ظلالًا منفصلة لشاشة واحدة بلا توكن معتمد.

## 2. الخطوط والكتابة العربية

- العربية تستخدم Cairo بأوزان 400/500/600/700/800، واللاتينية والأرقام التقنية تستخدم Inter بالأوزان نفسها عند الحاجة. هذه هي عائلات الويب المعرفة في `tokens.css`.
- أصول الخطوط محلية ضمن `@expo-google-fonts/cairo` و`@expo-google-fonts/inter`، وتُحمّل مرة واحدة في `src/app/_layout.tsx` قبل عرض مسارات التطبيق. لا تعتمد على تنزيل الخط من الشبكة وقت التشغيل.
- كل نص واجهة يستخدم `MadaText` من `src/components/MadaText.tsx`، لا `Text` مباشرة. يطابق المكوّن وزن الخط المحدد في `fontWeight` مع وجه الخط المحلي. استخدم `TextInput` بخط Cairo، واستعمل Inter صراحةً للهاتف والأرقام والمعرّفات LTR.
- الشاشات عربية وRTL افتراضيًا. الهاتف، الوقت/التاريخ عند الحاجة، رموز الأدوار، ومعرّفات الطلبات تُعرض LTR بوضوح. لا تعكس الأرقام أو تغيّر ترتيبها مع RTL.
- كل عنصر تفاعلي له مساحة لمس مستهدفة لا تقل عن 44dp، واسم مفهوم لقارئ الشاشة. لا تعتمد الحالة على اللون وحده.

## 3. تنظيم الكود ومسؤوليات الطبقات

```text
apps/mobile/
└── src/
    ├── app/             # Expo Router routes/layouts رفيعة
    ├── api/             # عميل API وعقود typed ومعالجة الأخطاء
    ├── auth/            # الجلسة، الهوية، SecureStore
    ├── authorization/   # كتالوج الأدوار وسياسات المسارات
    ├── components/      # MadaText وAppUi ومكوّنات Native العامة
    ├── theme/           # التوكنز والخطوط والطباعة
    └── features/        # وحدات نطاق تُضاف عند بناء التدفقات الفعلية
                         # instructor-home, schedule, attendance,
                         # evaluations, notifications
```

- ملفات `src/app/` مسؤولة عن التوجيه وتجميع مكوّنات الشاشة فقط. لا تضع فيها استدعاءات `fetch` مباشرة، أو قواعد عمل، أو تعريف صلاحيات مكرر.
- كل استدعاء بيانات يمر عبر `src/api/apiClient.ts`، وكل حالة عرض في الشاشة لها مصدر API معروف. تُفصل مهام كل نطاق داخل `src/features/<feature>/` عند البدء بربطها بدل تضخيم ملف route.
- `src/components/` للمكونات العامة القابلة لإعادة الاستخدام. لا تنقل مكوّنًا إلى هذه الطبقة لمجرد إعادة استخدامه مرة واحدة.
- لا تشارك CSS أو مكونات DOM الخاصة بالويب مع React Native. المشاركة المناسبة مستقبلًا هي عقود TypeScript/DTO مستقرة، لا واجهة الويب داخل WebView.

## 4. قواعد التنقل والأدوار والصلاحيات

1. **الخادم هو مصدر الهوية.** بعد تسجيل الدخول، يقرأ التطبيق الدور النشط والنطاق ومفاتيح الصلاحيات من `GET /api/v1/me`. لا يستنتج الدور من الهاتف أو اسم الحساب أو اختيار محلي.
2. **المستخدم لا يختار دورًا.** في الإصدار المحمول الحالي ترسل شاشة الدخول `accountType: "staff"` داخليًا فقط. `accountType` مسار مصادقة وليس role. لا تعرض قائمة أدوار ولا تسمح بتغيير الدور من الحساب.
3. **R04 هو الدور المحمول الأول.** كتالوج R00–R09 يبقى متوافقًا حرفيًا مع `backend/MadaAcademy.Api/Modules/Identity/RoleCatalog.cs`. الأدوار الأخرى لا تصل إلى شاشات R04؛ تظهر لها شاشة «الدور غير متاح» حتى يُنفّذ مسارها الخاص.
4. كل route محمي بـ`RouteGuard` وسياسة صريحة في `authorization/routeAccess.ts`. التبويب المخفي وتحذير الواجهة تحسين تجربة ودفاع إضافي فقط؛ لا يحلان محل فحص API.
5. كل فعل حساس يفحص permission key المعاد من `/me` في الواجهة **والخادم**. استخدم أسماء المفاتيح كما هي في عقد backend فقط، ولا تنشئ مفتاحًا أو دورًا من عندك.
6. الخادم يشتق الأكاديمية والفرع والنطاق من الهوية. لا ترسل `branchId` أو `academyId` أو قائمة طلاب كسلطة يحددها العميل، ولا توسّع الطلب من الهاتف.
7. `/me` الحالي يعيد عضوية نشطة واحدة ولا يوفّر endpoint لتبديل العضويات. إذا احتاج الحساب متعدد الأدوار إلى تبديل، يلزم عقد backend صريح قبل أي UI لذلك.
8. أي دور/permission غير معروف أو فشل في استعادة الجلسة يعامل بـ**المنع الافتراضي**؛ لا fallback إلى صفحة دور آخر.
9. Access token يبقى في الذاكرة قدر الإمكان، وrefresh token يستخدم `expo-secure-store`. لا كلمات مرور أو tokens في السجلات، ولا AsyncStorage لتخزين أسرار المصادقة.

## 5. قواعد الشاشات والبيانات

- **الرئيسية:** تبدأ بالاسم والتحية، ثم «مهمتك الآن»، ثم ما بعدها، ثم ملخص تحديثات إن وُجد. لا تعرض قائمة الصلاحيات على Home؛ مكان تفاصيل الدور والصلاحيات هو الحساب. لا تعرض عدد جلسات أو تقييمات إلا من استجابة حية موثوقة.
- المهمة الأساسية تفتح الإجراء التالي مباشرة، مثل الجدول أو الحضور إذا كانت الجلسة والصلاحية تسمحان. لا نضيف زرًا بلا وجهة فعلية.
- المهام التي تحتاج إجراء منفصلة عن التحديثات/التنبيهات المعلوماتية. لا تكرر التنبيه باعتباره مهمة.
- كل شاشة بيانات تنفذ الحالات الملائمة: loading، empty، error مع إعادة المحاولة، forbidden، success. فشل API لا يتحول إلى بيانات DEMO.
- الصور في `assets/` هي اتجاه بصري فقط. الأسماء والتواريخ والأعداد الموجودة داخلها ليست بيانات منتج ولا تُنسخ إلى fixtures الحية.
- الحضور: حالتا حاضر/غائب إجراءات سريعة، والحالات الأخرى وفق عقد backend. غير المحدد يبقى حالة محلية ولا يُرسل كحالة حضور. لا نعلن الحفظ قبل نجاح استجابة الخادم.
- التقييم يطابق العقد الحالي: درجة واحدة 0–100 وملاحظة بناءة، ثم حفظ مسودة أو إرسال للمراجعة؛ لا يُنشر للأسرة مباشرة من شاشة المدرب.
- الإشعارات تبقى منفصلة عن قائمة المهام. لا نعرض عددًا أو badge حتى يوجد مصدر بيانات موصول.

## 6. حدود الإصدار الحالي والقرارات التي تتطلب عقدًا

- الأولوية الحالية هي مسار R04. مسارات ولي الأمر والطالب وباقي الأدوار تُضاف كتدفقات مستقلة بعد تحديد الصلاحيات والـAPI وقرار المنتج، لا بمجرد نسخ شاشة المدرب.
- لا تفعّل offline attendance أو Push أو تبديل العضويات أو rubric متعددة الدرجات قبل عقد backend وسياسة مزامنة/اختبار واضحة.
- Home والجدول والمهام تستخدم `GET /sessions` ضمن نافذة محدودة (14 يومًا سابقة و45 يومًا قادمة) وتُحدّث عند الرجوع إلى الشاشة. لا يوجد backend work-queue مجمّع بعد؛ لذلك تعرض شاشة المهام الجلسات والإجراءات المتاحة ولا تدّعي أن تقييمًا بعينه مستحق.
- شاشتا الحضور والتقييم تتصلان بعقود backend الحالية. صلاحية القراءة لا تمنح الكتابة: الحضور يكتب فقط للمدرب المسند/البديل الذي لديه `attendance.write`، والتقييم يتطلب `evaluations.write`. R03 يظل على مسار مراجعة منفصل ولا يكتب تقييمات المدرب.
- إشعارات in-app لم توصل إلى واجهة Mobile حتى الآن؛ لا تعرض Home badge أو إشعارًا افتراضيًا.
- الشعار المرئي في الكود monogram مؤقت لأن أصل الشعار الرسمي لم يوجد في ملفات الريبو وقت إعداد القاعدة. لا تعتبره أصلًا نهائيًا؛ عند توفير ملف الشعار الرسمي استبدله دون رسم شعار بديل.

## 7. بوابات القبول لكل تغيير

قبل دمج أي تغيير للموبايل:

```bash
pnpm --filter @mada/mobile lint
pnpm --filter @mada/mobile typecheck
pnpm test
pnpm check
pnpm build
pnpm --filter @mada/mobile exec expo install --check
```

عند تغيير navigation أو native module أو typography، اختبر Expo export لمنصتي Android وiOS، ثم راجع RTL والخط وحجم النص ولوحة المفاتيح والـsafe areas على جهاز/محاكي. لا تعتبر Web preview بديلًا عن اختبار native.
